# 一些思考

## sdtlb_tag_item

断言 PA[47] 为 0, 因为 PA[47] 指 IO 空间, 内存池化只处理 MEM 空间, 不处理 IO 空间

当 wr_pa_up 为 0 时, 表示的一定是页式代换 (1GB), 此时 wr_pa_base 可以为任意值
当 wr_pa_up 非 0 时, 表示的一定是段式代换, 此时 wr_pa_base 虽然依然可以为任意值, 但断言 wr_pa_base 与 wr_pa_up 的组合不能越界

如果本来 mem 里是一张段式代换的 SDT_L1 表, 假设前 16G 为有效; 如果之后 OS 把这个表换成了后 16G 为有效, SDTLB 如何处理? (OS 通过 IOR::SDecoder_IS ,根据 PA 地址进行无效化?)

断言 SDTLB 里没有冲突的表项? (似乎很难实现, 也许写在 monitor 里更好?)

CORE 内 TLB 只有 tlb_tag.valid 是 ff, 其他 tlb_tag 字段以及 tlb_data 都是 latch, 是否沿用?

需要断言 128bit 的 hit vector 是宽松独热码 `$onehot0`

s_pfn 是 [17:0] 的, 所以本地 import 的内存空间不包括 IO 空间, 远程 export 的空间可以包括 IO 空间?

tlb 的替换策略选什么, CORE 内的 tlb 里是 "伪随机替换", 目前 SDTLB 里目前是 "最久没有被填充过的条目轮转替换"

tlb 的 entry 需要用 ram 实现吗, 还是用 ff 实现?

## req_hit_idx 是干什么的

先说结论: 在当前实现里它不是必需的, 但它是往上走时几个用途的公共入口

数据通路不需要它:命中数据是 128 份 rd_* 逐位 OR 出来的(未选中输出 0), 不需要知道下标;填充选址用的是独立的轮转指针 fill_ptr.所以纯从"现在能不能工作"看, 这个端口和它背后的优先级编码都可以删

它的价值在三个方向:

1. 按索引取数:算 SLA 要用命中条目的 pa_base[34:30](求 1GB 段内偏移).上层要么也 OR 汇总一份 rd_pa_base, 要么用 req_hit_idx 去索引/mux.以后若真把 Data 做成"单读端口 RAM"(设计方案 §表项格式 的写法), 读地址就是它 —— 那时它是硬需求
2. 替换策略/条目状态更新:设计方案 §替换策略 说"后续命中率不达标可换伪 LRU, 接口不变".伪 LRU 需要"这次命中了哪一条"来更新年龄位, 入口正是 req_hit_idx(现在的轮转策略只看装填, 用不上它)
3. 调试/覆盖率/监控:能观测"哪一条命中"(命中分布, 是否总压同一条, 冷热分析).这也是设计方案 §命中判断 里"若多命中取索引最小的条目"这句的另一半 —— 没有下标, 优先级编码本身就没意义.我那份 /tmp 单元自检也是靠它反推"这次装填落在哪一条"

建议的定夺口径:如果下一步决定 SLA 也走"OR 汇总 rd_pa_base", 且短期内不换伪 LRU, 就把它连同优先级编码一起删掉(端口更干净);如果打算走"按索引读/mux"或想留观测口, 就保留.你定一个, 我改 sdtlb 时一起做掉(以及要不要顺手加 rd_pa_base/rd_pa_up 给上层算 SLA, 这是上一轮留的 A/B 选择)
