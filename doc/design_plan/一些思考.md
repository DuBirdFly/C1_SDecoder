### 寄存器的宽度

### 关于压缩队列

很难做同地址队列压缩, 因为页表是段页混合的, 很难做到说后一个 pa 请求就一定和前一个 pa 请求命中了同一个段

最多最多压缩 [46:30] 完全相同的 pa 请求

但对于 [46:30] 不同, 但确实命中了同一个段的 pa 请求, 是无法在 MISS_FIFO 处压缩的

感觉不如在实际查表前看一眼 tlb 是否能够命中

### TLB 应该只使用一个 CAM 口

现在有 2 个请求类型会 CAM 查 TLB 是否命中

- req_\* 直接请求 tlb 查找
- ptw 访存请求前会先查 tlb 是否命中

鉴于 page walk 是小概率事件, 为了时序和面积考虑, 分时复用 1 个 CAM 口

鉴于 CAM 口只有 1 个, 所以同一拍只能有 1 个 CAM 请求, 所以优先看 ptw 的 CAM 是不是命中

或者更具体一点, 当 page walk 在查看 CAM 的时候, req_ready 要被阻塞

所以现在应该有 3 个 req_ready 阻塞源

1. 当 CAM 正在被 page walk 使用时
2. 当 inv_* 正在被处理时
   1. 无论 inv_all 还是 inv_pa, 都要等 MISS_FIFO 排空才能释放 req_ready
3. 当 MISS_FIFO 已满时

### fill_\* 与 req_\* 恰好同一拍处理到同一个 tlb entry

核心里面 tag 命中后的 hit_vector 会打 1 拍吗? 我是打了 1 拍的.

这种情况只会出现在 TLB 满的情况下, 不算多见, 也就是 TLB 必须淘汰一个正在使用的 entry 的情况

如果 hit_vector 不打拍, 那应该没啥问题
如果 hit_vector 打了 1 拍的情况下, "同一拍" 或 "fill_\* 滞后 req_\* 恰好一拍" 都可能会有问题

当然也和 fill 的行为有关, 分 2 拍进行 fill 就可以规避这个问题

### S_PFN[47] 是否使用

s_pfn 是 [17:0] 的, 所以本地 import 的内存空间不包括 IO 空间, 远程 export 的空间可以包括 IO 空间?
export 的空间其实不包括 IO 空间, 只是为了兼容性, 所以 s_pfn[17] 也要保持
事实上, 在下一个版本, S_PFN 的位宽会从 [47:30] 修改为 [52:30], 因为要以虚地址访问 (UBA 是虚地址)

### 与 LCPM 的接口

LCPM 作为核外一致性处理部件, 一方面要判定是本地内存请求还是远端内存请求 (远端内存请求发给 SDecoder), 一方面要处理访存请求
所以 SDecoder 与 LCPM 之间有 2 组接口 (暂定):

1. 远端内存请求接口: `req_valid`,`req_pa`
   1. 为了尽可能无阻塞传输, 需要 bypass-fifo 缓存 pa 请求
   2. 用 bypass-fifo 会有一致性问题吗?
      1. 比如 fifo 里有很多待处理的 pa 请求, 但软件在此期间 inv_all 了 sdtlb,
         然后 mem 里的 tlb_entry 置为 invalid, 那就很可能导致 fifo 靠后的请求
         无法正确处理
2. Page Table Walk 访存请求: 使用数据宽度 16B 的 AXI Lite 接口

## 已定

### sdtlb 时序

sdtlb_tag 组合逻辑输出 hit_vec, sdtlb_data 打 1 拍后使用 (核内 DTB 是这么做)
在 tlb_hit 的前提下, req_valid 有效的 1 拍后, rsp_* 的数据才是有效的
注: **有效**指的是 clk 上升沿时, 该位置位
注: 考虑到流水线处理, req_valid 可以拍拍有效

### CAM 端口

tag 使用单端口的 CAM (Content Addressable Memory, 内容可寻址存储器)
Core DTB 使用双端口 CAM TLB, 是因为超标量处理器一拍可能同时处理 2 条 load 类指令, 为避免串行, 所以要用多端口 CAM

### PA[47] 是否使用

PA[47] 到底还要不要用?
还要用.
PA[47] = 1 是 IO 空间, 但因为只有 4K 张一级表 (共 128TB Mem 空间), 内存池化也只处理 MEM 空间
可以说 sdecoder 的 pa 请求要断言 PA[47] 为 0
虽然 sdecoder 的 pa[47] 几乎没有意义, 但在某些地方依然保持 pa[47] 的存在, 比如

1. sdecoder 的 pa 请求位宽 [47:0], 但断言 pa[47] 为 0
2. 一级表 SDT_L1 的基地址 IOR::SDT_L1_BASE 里, pa[47] 也要保持, 但写该 ior 时, 断言 pa[47] 为 0
3. 一级表 SDT_L1 的 entry 里, SDT_L1.L2_BASE[47] 也要保持, 但 page table walk 找 SDT_L2 时, 断言 SDT_L1.L2_BASE[47] 为 0
4. 快表 SDTLB 的 SDTLB.TAG.PA_Base[47] 也要保持

### 无效化操作

什么时候软件进行无效化操作?
(如果本来 mem 里是一张段式代换的 SDT_L1 表. 假设前 16G 为有效, 如果之后 OS 把这个表换成了后 16G 为有效, SDTLB 如何处理?)
OS/软件 通过 IOR::SDecoder_IS 或 IOR::SDecoder_IA, 根据 PA 地址进行无效化
但按照核心的经验, 如果 OS/软件 忘记进行无效化操作, 就会导致 pa 访问的是 tlb 里的旧 entry, 非常难查问题

另外, 如何断言 SDTLB 里没有冲突的表项?
纯断言似乎很难实现, 也许写在 monitor 里更好?

### tlb entry

tlb entry 使用 ff 还是 latch, 甚至更激进的无 rst_n 的 ff, 或是 ram?
CORE 内 TLB 只有 tlb_tag.valid 是 ff, 其他 tlb_tag 字段以及全部 tlb_data 字段都是 latch, 选择沿用

### tlb 的替换策略

tlb 的替换策略选什么?
核内 ITB 和 DTB 是 "伪随机替换", ATLB 是 $onehot 左移循环寄存器
为简化设计, tlb 也选 $onehot 左移循环寄存器
