# AI 易错点

## 不该对 Latch 本身做修改

Latch 有个特性是**禁止同拍同时进行读写**, 否则可能导致数据在被稳定锁存前就被读取, 甚至引发竞争, 使电路状态变得不可预测 (甚至 Latch 的竞争行为在不同 EDA 根据中可能表现不一, 这是对仿真与综合的很大挑战)

一种可以让 Latch 同拍同时进行读写的方法是使用 **两相非重叠时钟**: 通过两个相位严格不重叠的时钟分别控制 "读 Latch" 和 "写 Latch", 确保在任何时刻, 针对同一数据通路的读和写操作发生在隔离的时间窗口内

曾经 AI 尝试使用类似于 **两相非重叠时钟** 的方法驱动 Latch, 主动让 "读 Latch" 和 "写 Latch" 分别 "与" 上时钟时钟本身 (一个用 clk, 一个用 ~clk), 这样 "读 Latch" 和 "写 Latch" 就在同一拍时钟内分到了 2 个时钟的电平区间 (一个仅 clk 高电平有效, 一个仅 clk 低电平有效)

**两相非重叠时钟**固然能解决 Latch 的同拍读写问题, 但用 Latch 主要就是为了其 "面积, 速度, 功耗" 的优势, **两相非重叠时钟**相当于把 Latch 的优势区间又给抹掉了大半, 体感上应该还不如 FF 来得好用

再者, 设计方案里明确表示了希望 RTL 工作在单时钟域下, 不希望额外引入时钟, 使用**两相非重叠时钟**违背了 spec 的初衷

事实上, 最后设计方案里给出的解决方案是, 当某一拍正在做 "写 Latch" 这个操作时, 反压 Latch 的读端口, 所以断言 "读 Latch" 和 "写 Latch" **不可能同时发生**. 这个解决方案当然是有代价的, 因为反压 Latch 的读端口时, 数据通路相当于被阻塞, 是一定程度上会影响到性能的发挥. 但是考虑到写 Latch 只会发生在 Page Walk 的完整访存之后, "写 Latch" 的概率很低, 这个代价可以被接受

## 不该在 RTL 里主动给 Latch 做打拍寄存器

这是一个仿真伴生问题, 因为仿真时一般都用 interface 的 clocking block 驱动 input 信号 (事实上因为 delta time 的问题, 不是 clocking block 也很可能导致该问题), 而 clocking block 一般会让信号的值从一个 clock 的上升沿后一点点时间一直持续到下一个 clock 的上升沿后一点点时间, 这就导致了事实上 "写 Latch" 的输入信号事实上跨越了 2 拍, 从而很可能在第二个 clock 的上升沿后面的那一点点时间里, Latch 的 write enable 输入信号还有效, 但 write data 输入信号已经发生了改变, 这就会导致仿真行为和预期不符

解决上述问题最简单的方法就是让 Latch 的 input 信号来自于 FF 而不是直接由 Testbench 驱动, 这样就能规避 testbench 和 rtl 二者本身的竞争问题 (不然去研究 IEEE SystemVerilog 手册的 "Scheduling semantics" 更是一种灾难的行为)

但是写 Testbench 时, 不能因为上述原因主动修改 rtl 的代码, 给 rtl 代码里的 Latch 前主动给 "读 Latch" 或 "写 Latch" 前加 FF 打 1 拍, 因为 RTL 对时序节拍要求一般比较严格, 尤其是 Latch 一般都在数据通路上, 打拍很可能导致其他控制通路整体要大修改 (要改也是其他地方改, 比如 SDTLB 这种 Latch 相关模块, 只需要约定 "上游保证读端口和写端口的接口信号来自于 FF" 即可满足仿真条件)

所以 testbench 应使用 `wrapper_sdtlb.sv` 作为 sdtlb 的顶层, 而不是直接例化 sdtlb, `wrapper_sdtlb.sv` 里仅对仿真而言做了输入打拍操作, 这样即不会影响 rtl, 又可以解决这个仿真问题
